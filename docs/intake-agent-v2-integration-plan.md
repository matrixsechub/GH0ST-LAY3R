# Intake Agent v2 — HQ Integration Plan

**Status: design specification**
**Branch: feature/intake-agent-v2-hq-bootstrap**
**Scope: gh0st-lay3r only** — ttx-operator-shell changes are a separate,
pending deliverable that requires `ttx-operator-shell` repo access approval.

---

## 1. Purpose

Intake Agent v2 (`IntakeAgentV2`) adds structured lifecycle tracking and
operator-action hooks to the existing intent-ingestion flow. Where the four
existing constellation agents observe substrate state and produce advisory
outputs, `IntakeAgentV2` is the queue-management and operator-surface layer:
it classifies every intent into a lifecycle stage, exposes queue metrics to
HQ observability endpoints, and surfaces the set of operator actions available
for each intent.

**What this is not:** a dispatcher, a real queue store, or a MSHOPS.NET
backend. `IntakeAgentV2` runs inside the existing `GhostLayerEngine` pipeline
and produces structured output. Persistence, real queue management, and
operator-action routing are MSHOPS.NET responsibilities.

---

## 2. GOV-4 Gate

`IntakeAgentV2` is defined in `agents/constellation.py` and registered in
`agents/registry.yaml` with `status: experimental`. It is **not** added to
`create_default_engine()`'s agent list — that registration is the GOV-4
gate. The operator (`operator_id: lupe`) must explicitly approve promotion
from `experimental` to `active` and authorize the runtime registration before
the agent runs inside the engine. Until then, the agent class exists for
design validation and serve.py endpoint testing only.

## 3. Lifecycle Stages

`IntakeLifecycleStage` (defined in `core/registry.py`):

Implemented flow (enforced by `_INTAKE_VALID_TRANSITIONS` in `scripts/serve.py`):

```
received ──► validated ──► queued ──► processed
```

Every other transition (skipping a stage, going backwards, leaving
`processed`, or entering or leaving `escalated`) is rejected with HTTP 422
and leaves state and the audit log untouched. Only the newest record of an
intent can be advanced (an older `lifecycle_id` gets 409), and
`intent_id`s are always generated by the server (`POST /api/register`
rejects one sent by the caller), so a chain can never be forked, restarted,
or claimed in advance. Moving into and out of `escalated` is operator-only —
see §4.

| Stage        | Status       | Meaning                                                  |
|--------------|--------------|----------------------------------------------------------|
| `received`   | implemented  | Submission acknowledged via `POST /api/register`         |
| `validated`  | implemented  | Passed initial checks; grants full marketplace access    |
| `queued`     | implemented  | Waiting in the processing queue                          |
| `processed`  | implemented  | Intake flow finished; `resolved_at` is set               |
| `escalated`  | implemented  | Operator review; reached only via the `escalate` action  |
| `processing` | schema only  | Pre-TTX stage, kept for schema compatibility             |
| `completed`  | schema only  | Pre-TTX stage, kept for schema compatibility             |

Lifecycle records are append-only: each transition appends a new
`IntakeLifecycleRecord` (in `core/registry.py`) with the same `intent_id`,
leaves the previous record unchanged, and writes an `AuditEvent` with
`event_type: "intake.stage_changed"` (payload: `from_stage`, `stage`,
`previous_record_id`).

### Marketplace access

While any intake escalation is open (`pending` or `acknowledged`, for an
intent that has lifecycle records), `GET /marketplace` reports `review`
for everyone, so approving one intake cannot grant access while another is
under review. GOV-3 escalations raised by `POST /intents` have no intake
and do not gate the marketplace. Otherwise it is `full` while any intake
currently has access, and `observer` if none does.

An intake gains access when it reaches `validated`, either through the
operator's `approve` or the token-gated transition. It loses access only
when the operator escalates or closes it. Everything a caller can do without
the token, such as registering intakes or moving them through `queued` and
`processed`, leaves access unchanged. Annotate and reassign leave it
unchanged too. So only the operator can move the marketplace out of `full`.

| State                                          | `mode`     | `access` | Banner |
|------------------------------------------------|------------|----------|--------|
| an intake escalation is open                   | `review`   | `false`  | "IntakeAgentV2: Operator Review in Progress — Access suspended pending resolution." |
| otherwise, some intake has access              | `full`     | `true`   | none |
| otherwise                                      | `observer` | `false`  | "IntakeAgentV2: Access Pending — You are in Observer Mode." |

There is no identity layer, so this is one global state for the server,
not per-user. The register, transition, and action responses include the
same global state.

## 4. Operator Actions

Implemented by `POST /intake-agent-v2/lifecycle/action` (§6), enforced by
`_OPERATOR_ACTIONS` in `scripts/serve.py`. `IntakeOperatorAction` is
defined in `core/registry.py`.

| Action     | Allowed from                         | Result                                   |
|------------|--------------------------------------|------------------------------------------|
| `approve`  | `received`, `escalated`              | → `validated` (full marketplace access)  |
| `escalate` | `received`, `validated`, `queued`    | → `escalated`; opens an `EscalationEvent` |
| `close`    | `received`, `validated`, `queued`, `escalated` | → `processed`; sets `resolved_at` |
| `reassign` | `escalated`                          | stays `escalated`; sets `assigned_lane` (required `lane`) |
| `annotate` | any stage, including `processed`     | no stage change (required `notes`)       |

Any other action/stage pair is rejected with 422 and no side effects.

**Operator-only.** The caller must send `Authorization: Bearer <token>`
matching the `GHOST_OPERATOR_TOKEN` environment variable the server was
started with (constant-time comparison; the `Bearer` scheme name is
case-insensitive). The token is checked before the request body is read. If
the variable is unset, the endpoint returns 403 for everyone (fails
closed); a missing or wrong token returns 401. Actions are recorded as
performed by the registered operator (`lupe`). The token travels over
plain HTTP, so on a non-loopback bind (e.g. `--host 0.0.0.0`) operator
actions are refused (403) unless the server is started with
`--allow-insecure-operator`, in which case it prints a warning.

**Reads are not protected.** Every GET endpoint, including
`/intake-agent-v2/lifecycle`, `/escalations`, `/audit`, and
`/cockpit/intake`, is unauthenticated, so operator notes, escalation
reasons, and assigned lanes are readable by anyone who can reach the
server. Keep it on the default localhost bind.

**Escalation linkage.** `escalate` opens a `pending` `EscalationEvent` for
the intent (`trigger_rule: "operator-manual"`, `severity` from the request,
default `high`, `agent_ids: ["intake-agent-v2"]`). It appears in
`GET /escalations` and `HQHealthRecord.open_escalation_count`. `approve`
and `close` end every open escalation for the intent, from any stage:
`approve` marks them `resolved` (action taken) and `close` marks them
`dismissed` (no action needed), per the Escalation Lifecycle in
`AGENT_HQ.md`. `reassign` and `annotate` leave them open. `operator-manual` is not a GOV-n rule: no
existing rule covers an operator escalating by hand.

Each action appends an `IntakeLifecycleRecord` with `operator_action` set
and writes an `intake.operator_action` audit event; actions that change the
stage also write `intake.stage_changed`, and escalation changes write
`escalation.created` / `escalation.status_changed`.

The set of available actions for a given intent is returned by
`IntakeAgentV2.run()` in the `operator_actions_available` field, reflecting
the current stage and volatility.

## 5. HQ Schema Additions (core/registry.py)

### New type aliases
```python
IntakeLifecycleStage = Literal[
    "received", "validated", "queued", "processing",
    "processed", "escalated", "completed",
]
IntakeOperatorAction = Literal["approve", "escalate", "close", "reassign", "annotate"]
```

### IntakeLifecycleRecord dataclass
Fields: `id`, `intent_id`, `stage`, `created_at`, `updated_at`, `source`,
`operator_action` (Optional), `operator_notes`, `assigned_lane` (set by
`reassign`, carried forward), `resolved_at` (Optional).
`type` discriminator: `"intake-lifecycle"`. Added to `RegistryRecord` union.

### HQHealthRecord intake fields (additive, all default to 0)
- `intake_received_count`, `intake_validated_count`, `intake_queued_count`,
  `intake_processed_count` — the implemented flow
- `intake_processing_count`, `intake_completed_count`,
  `intake_escalated_count` — schema-only stages
- `intake_queue_depth` — legacy alias of `intake_queued_count`

These are populated by `scripts/serve.py`'s `_compute_hq_health()` from the
`_intake_lifecycle` list at request time.

## 6. serve.py Extensions

Endpoints added to `scripts/serve.py`:

| Method | Path | Purpose |
|--------|------|---------|
| GET  | `/agents/intake-agent-v2` | Registry entry |
| GET  | `/intake-agent-v2/lifecycle` | All lifecycle records, append order |
| GET  | `/intake-agent-v2/metrics` | Per-stage counts |
| POST | `/api/register` | Public intake submission → `received` record |
| GET  | `/marketplace` | Access mode + banner from latest stage |
| POST | `/intake-agent-v2/lifecycle/transition` | Advance one record one stage (token required to reach `validated`) |
| POST | `/intake-agent-v2/lifecycle/action` | Operator action (token required) |
| GET  | `/cockpit/intake` | Read-only operator panel |

> **Security:** reaching `validated` (full marketplace access) needs the
> operator token, through either the `approve` action or the transition
> endpoint. `POST /api/register`, the `validated → queued → processed`
> transitions, and all GET endpoints have no authentication. Run `serve.py`
> on localhost only (its default bind).

### GET /agents/intake-agent-v2
Returns the registry entry for `intake-agent-v2` from `_registry["agents"]`.
Looks up by `id == "intake-agent-v2"`. Returns 404 if not found (e.g., if
the fallback registry doesn't include it).

### GET /intake-agent-v2/lifecycle
Returns the `_intake_lifecycle` list — all `IntakeLifecycleRecord` dicts
recorded since server start, in append order. Empty list `[]` on a fresh
server. No filtering in this stub; MSHOPS.NET adds pagination and filtering.

### GET /intake-agent-v2/metrics
Returns a metrics snapshot:
```json
{
  "received_count": <int>,
  "validated_count": <int>,
  "queued_count": <int>,
  "processed_count": <int>,
  "processing_count": <int>,
  "escalated_count": <int>,
  "completed_count": <int>,
  "total": <int>
}
```
Counts are stage entries, not intents per current stage: one intent
walked to `processed` counts once in each of the four TTX stages. Records
that keep an intent in the same stage (`annotate`, `reassign`) are not
counted; `total` is the sum of the stage counts.
The same counts are surfaced in `HQHealthRecord`'s `intake_*_count` fields.

### POST /api/register
Body: `{"raw": "...", "source": "...", "notes"?: "..."}`. Sending
`intent_id` is rejected (400); the server generates it.
Returns 201 with `{"lifecycle": <record>, "marketplace": <state>}`.

### GET /marketplace
Returns `{"mode", "access", "banner", "latest_intake_stage",
"open_intake_escalations", "total_submissions"}`.

### POST /intake-agent-v2/lifecycle/transition
Body: `{"lifecycle_id": "...", "to_stage": "...", "notes"?: "..."}`. Returns
200 with `{"previous", "current", "marketplace"}`; 400 for missing fields;
404 for an unknown `lifecycle_id`; 409 if `lifecycle_id` is not the
intent's newest record; 422 for a disallowed transition. Moving to
`validated` requires `Authorization: Bearer <GHOST_OPERATOR_TOKEN>`, checked
before the record lookup (401/403, same rules as the action endpoint), and
is audited with the operator as the actor. `queued` and `processed` need no
token.

### POST /intake-agent-v2/lifecycle/action
Header: `Authorization: Bearer <GHOST_OPERATOR_TOKEN>`. Body:
`{"lifecycle_id": "...", "action": "...", "notes"?: "...", "lane"?: "...",
"severity"?: "low|medium|high|critical"}`. Returns 200 with
`{"previous", "current", "escalations", "marketplace"}` (`escalations` lists
the escalation records opened or closed by this action). Errors: 401/403
(auth, checked first), 400 (missing or non-string fields, empty `notes` for
`annotate`, empty `lane` for `reassign`, bad `severity`), 404 (unknown
record), 409 (stale record), 422 (unknown action, or action not allowed from
the stage).

All POST endpoints reject a body that is not a JSON object (400), a
non-numeric `Content-Length` (400), or a body over 64 KiB (413, not read);
string fields must be strings (400).

### GET /cockpit/intake
Read-only: agent status, GOV-4 status, routing-table entry count, per-stage
counts, full timeline, and the last 10 `received` records.

Module-level state: `_intake_lifecycle` (append-only list of
`IntakeLifecycleRecord`-shaped dicts) and `_routing_table` (four
`RoutingTableEntry`-shaped dicts routing `intake`/`register`,
`access-request`, `paywall`, and `register-transition` tags to
`intake-agent-v2`). `POST /intents` records matched routing entries in its
`intent.submitted` audit payload but never runs `IntakeAgentV2`.

`_compute_hq_health()` populates `intake_received_count`,
`intake_validated_count`, `intake_queued_count` (alias `intake_queue_depth`),
`intake_processing_count`, `intake_processed_count`,
`intake_completed_count`, and `intake_escalated_count`.

Regression coverage: `tests/test_intake_agent_v2.py`,
`tests/test_operator_actions.py`.

`_REGISTRY_FALLBACK["agents"]` updated to include the `intake-agent-v2` entry
matching `agents/registry.yaml`, so the endpoint is reachable even without PyYAML.

## 7. Audit Event Types (intake domain)

| event_type               | Produced by                                   |
|--------------------------|-----------------------------------------------|
| `intake.stage_changed`   | Any lifecycle stage transition                |
| `intake.operator_action` | Any operator action (approve/escalate/etc.)   |
| `escalation.created`     | `escalate` action                             |
| `escalation.status_changed` | `approve` / `close` from `escalated`       |

These follow the existing dot-notation convention in `AuditEvent.event_type`.
`scripts/serve.py` appends them to its in-memory `_audit_log` (MSHOPS.NET
owns the persistent write path). Read the intake events with
`GET /audit?target_type=intake-lifecycle` and the escalation events with
`GET /audit?target_type=escalation`.

## 9. SCOPE-LOCK Compliance

- No Cloudflare Workers or wrangler deployment assumed.
- No MSHOPS.NET backend assumed as deployed — treated as design target only.
- No changes to `core/engine.py` or `create_default_engine()` — GOV-4 gate.
- All new serve.py state is module-level and in-memory (no external store).
- `IntakeAgentV2` class is defined but not registered — this is the
  explicit, documented GOV-4 gate boundary.
- Escalation and audit linkage is additive: new `intake.*` event types
  follow the existing `AuditEvent` schema without changing it.
